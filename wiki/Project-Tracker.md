# Project Tracker

Last reviewed: 2026-09-12.

This is the only human-maintained XAIOS project tracker. Roadmaps, milestones,
phase plans, open decisions and risks are consolidated here, and the Wiki keeps
no other planning page. It records what each item's state is and what would
change it -- not how the work was done. That reasoning belongs in the commit
that did it and in the comments beside the code.

## Where the tree stands

The ten aggregate targets -- `qemu-core-os-rc`, `qemu-full-os-rc`,
`qemu-developer-ux`, `qemu-operations-closure`, `qemu-network-adversarial-gate`,
`qemu-readiness-gate`, `qemu-post51-gate`, `qemu-qualification-readiness`,
`qemu-100-gate` and `qemu-release` -- were re-run serially on 2026-09-12. Eight
passed. `qemu-readiness-gate` and `qemu-full-os-rc` both failed on the same leg,
`qemu-fault-matrix`, and that failure was this machine's accumulated durable
volume rather than the guest: the three controlled-fault scenarios never ran,
because the boot died first in an unrelated self-test. It is `B-51`, it is
fixed, and `qemu-fault-matrix` passes in isolation on the same commit that
failed. **The two aggregates have not themselves been re-run since that fix**,
so no statement here about their status is newer than that.

They are run serially deliberately: these assert on boot markers and timings,
and this machine cut a `qemu-smoke` boot short at load average 30 and passed it
at load 9 with no change in between. The consolidated report deliberately
retains `physical_qualification=false`.

What *is* current, against `7df4fc8`, the commit build 6 was cut from:
`make release-check` passes, which requires `docs-check`, a
`check-release-package` run against the published note, and a `local-gates`
record naming that exact commit. That record covers six gates including both
hypervisors -- `vmware-fusion-smoke`, `vmware-fusion-framebuffer-gate`,
`vz-gate`, `hypervisor-memory-matrix`, `release-image-gate` and
`vz-stress-gate`. `boot-media-gate` (72 checks) and `vm-package-gate` (five
kits) also pass on the released files.

That is emulated evidence and nothing more. **No result on this page is
physical-hardware evidence, and no released build has been booted on physical
hardware.**

`TESTING` in the table below, which here means the fix or the measurement is
still owed rather than that the code is untried.

Three things are open that are not defects:

- **No physical hardware, on any architecture.** Every result on this page comes

  `serve-netboot.sh` has never served a real machine on any architecture.
- **Two external decisions block their own work** and nothing here moves them:
  `OD-004` (production trust-root custody) and `OD-008` (pinning an official

- **The two aggregate targets that failed on 2026-09-12 have not been re-run
  since the fix that explains them.** `qemu-fault-matrix` passes in isolation;
  `qemu-readiness-gate` and `qemu-full-os-rc` have not been asked again.

One step timed out once and did not reproduce; it is `B-39` rather than a

## Status codes

| Code | Meaning |
|---|---|
| `TESTING` | Implemented, but the current acceptance run or physical qualification is still underway. |
| `IN PROGRESS` | Active implementation is incomplete. |
| `NOT STARTED` | No qualifying implementation has begun. An interface or fixture alone does not count. |
| `BLOCKED` | Work cannot proceed until the stated external decision or dependency is resolved. |
| `FAILED` | The latest required acceptance gate failed; the failure evidence must be linked in the item. |
| `DEFERRED` | Postponed on purpose. Not blocked by anything external and not abandoned -- it is simply not being worked on now, and saying so is more honest than leaving it among the open items. |
| `NEEDS HARDWARE` | Implemented as far as it can be here, and the remaining evidence can only come from physical machines. Not on the active work list: no amount of effort in this environment moves it, and leaving it among the open items makes the list read as further behind than it is. |

Resolved items carry no status code. They move to a **Resolved, kept for
reference** table in their own section, which records what the item was and
what closed it. They are not deleted, because their identifiers are cited
from the code, the gates and the release notes.

QEMU status proves correctness and ABI behavior only. Physical support and
performance require immutable evidence under the
[benchmark contract](https://github.com/Pummelchen/XAIOS/blob/main/docs/BENCHMARK-CONTRACT.md).

## Open bugs

Defects with no fix in place, followed by resolved ones kept for reference.

A resolved row is not deleted, because its identifier is cited from the code,
the gate or the release note that closed it -- `B-14` appears in five release
notes and a gate docstring, `B-25` in ten files -- and a citation that resolves
to nothing is worse than a short row. The reasoning behind each fix stays in
the commit that made it and in the comments beside the code; this table records
only what the defect was and what closed it.

| ID | Defect | Affects | Status | Notes |
|---|---|---|---|---|
| B-43 | A session stalls ~19 s and the guest says nothing about it | VMware Fusion ARM64 | `TESTING` | **The premise originally written into this row was wrong** -- it said the server was serving a later connection while an earlier sat untouched, but the soak's round is strictly sequential, so two sequential events were read as concurrent. With that gone there is no reason to expect a starvation bug and none is there. The 18 s is the macOS client's own patience, not a guest constant. **Three Fusion load soaks have now run against the instrumentation `B-44` added, and it did not recur:** 3911 verified round trips of 256 KiB across three boots, every file byte-identical, `service loop stalled` **zero**, `stack was not polled` **zero**, and the worst poll gap 202 ms -- two orders of magnitude below the stall this row describes. That is evidence of absence rather than a cause, and the row stays open because absence over three runs is not proof. **What the search established remains worth more than the row asked for:** `network_poll_tick` has no timer, no interrupt and no thread, so sshd is the machine's network thread and any pause in its loop is a total network outage -- see `B-44`. **To close:** a recurrence carrying one of the three console lines. |
| B-48 | Every file write committed the whole metadata region | all four | `FIXED` | `write_metadata` rebuilt the region and wrote every sector of it however little moved: **1281 sectors, 640 KiB, for a 32-byte append**, measured at the block device. Nearly all of it is the node table, and an append changes one node. That is why `B-45` took file bytes to almost nothing and per-record time did not move. A commit now writes only the sectors that differ from what the target slot already holds: **4 sectors, 2 KiB**, on the same measurement. Two shadows, because the slots alternate -- a commit targets the slot mount would *not* currently choose, so what it replaces is two commits old and a single previous buffer would compare the wrong one. A shadow is believed only after its write has flushed, and any failure marks it unknown so the next commit writes the region whole; the cost of being wrong is a metadata sector silently keeping an old value, so conservative is the only acceptable direction. Costs 2.5 MiB of static buffers. **Evidence:** `tests/storage/test_xaiboot_fs_write_cost.c` counts sectors at the block device, so the figure is what the disk sees rather than a claim, and it fails against the previous code. `qemu-power-loss-gate`, `qemu-crash-safety-gate` and `qemu-write-ordering-gate` all pass -- which is the bar this row asked for, because the change alters which metadata sectors reach the disk. |
| B-50 | `qemu-ssh-connection-rate-gate` cannot create its condition on this host | repository | `TESTING` | The gate opens 121 connections through QEMU's host forwarding inside the limiter's 60 s window and gets `{banner: 114, silent: 2, unreachable: 5}`. **The gate's own bug is fixed and was the serious half:** `unreachable` and `silent` counted as neither served nor refused, so one run emitted both "only 113 of the first 120 were answered" and "all 121 were served, so the limit did not fire". It now reports `INCONCLUSIVE, not a guest defect` and exits non-zero. **The experiment this row proposed has been run and its hypothesis is falsified.** Pacing the opens at 397 ms -- derived from the window, not picked -- produced `{banner: 114, silent: 2, unreachable: 5}`, identical to the tight loop, across a 2.6x spread in wall time (30.6 s against 80.8 s). A host rate or burst limit would not survive that. The pacing was reverted rather than kept: it does not help and it pushes the case past the 60 s window, so the limiter can no longer fire. **What the run did surface** is the guest reporting, through `B-44`'s instrumentation, `network: stack was not polled for ms=30839` and `sshd: service loop stalled ms=30840 phase=accept`. **Cause and consequence are not established and are not being guessed at:** the five failed opens cost the host a 4 s timeout each, which could account for most of 30 s, so the outage may follow the failures rather than produce them. sshd's loop calls a non-blocking accept and then `wait_events`, which does poll, so a 30 s gap while idle is not explained either way. **To close:** a run that timestamps the host's opens against the guest's poll gaps, so the order of the two is a measurement rather than an inference. |
| B-55 | Sixteen extents was a reachable ceiling; it is now sixty-four | all four | `TESTING` | A file may be scattered across at most `XBFS_V6_MAX_EXTENTS` runs. At 16 that was reachable: on a v5 volume -- 8192 blocks, 256 nodes, which is what every machine here boots -- the smallest hole a full volume can be cut into is 16 blocks, so a maximum-size 512-block file needs about **32** extents. Sixteen could not serve it. `B-52` made that far harder to reach by taking the longest runs first; it did not move the limit. **Raised to 64, which covers that case with headroom.** It costs 768 bytes per node and 0.75 MiB across the node table, and the metadata region grows from 2560 to 3584 sectors. That was worth weighing when every commit rewrote the whole region; since `B-48` a commit writes only the sectors that changed, so a larger table costs space rather than write amplification. **The v6 node layout changes and nothing migrates it** -- the project is early enough that breaking the format is cheaper than carrying a conversion. The v5 on-disk format is a block list and is untouched; a v5 volume written by the previous build still mounts, fscks clean and snapshots, which was checked. **Still a raised ceiling and not a removed one.** A maximum-size file on a fragmented v6 volume would need about 2048 extents, and 512 inline costs 25 MiB of buffers. Removing it properly means indirect extents: a node that points at an overflow block when it runs out of inline room. **Not claimed as tested:** the node limits make a case needing more than 16 extents awkward to construct cheaply -- a v6 volume cannot be filled through the whole-file path at all, because 2M blocks at 512 per write exceeds 1024 nodes -- so this rests on the arithmetic above and on the existing suite continuing to pass, not on a test that exercises the new depth. |
| B-60 | `qemu-operations-closure` required `ssh reboot` to exit cleanly over the connection the reboot destroys | repository | `TESTING` | `reboot` is the one command whose success ends the connection carrying it. Whether `ssh` exits 0, exits non-zero, or hangs to its own timeout is a race with the guest's shutdown, and on a runner with no hardware virtualisation the guest loses it: CI failed with `subprocess.TimeoutExpired` on the word `reboot`, from 2026-09-02. Nothing was gained by asserting it -- the gate checks the console immediately below for the lifecycle record's third durable write and the guest's third ready marker, which says the machine *came back* rather than that it accepted the request. The call now tolerates a timeout or a non-zero exit. **Weaker evidence than the rows around it, and said so deliberately:** this cannot be reproduced here, because it passes on this Mac, which is the whole problem. The basis is the CI traceback and the redundancy argument; the gate passes locally with the change, and the next CI run is what settles it. |
| B-61 | Two userspace linker scripts never collected RISC-V's small-data sections | riscv64 | `FIXED` | A hosted C99 application reached userspace and then failed its first `printf`, exiting 1 after a single syscall, which `kmain.c:1427` asserts on. It cost the RISC-V CI job **every run it has ever had** -- 66 of them, never green. `userspace/libc/linker.ld` and `userspace/init/linker.ld` collected `.data .data.* .ldata .ldata.*` and `.bss .bss.* .lbss .lbss.* COMMON` and never named `.srodata`, `.sdata` or `.sbss`. Under a toolchain that emits them they were placed as orphan sections wherever the linker chose. `kernel/arch/riscv64/linker.ld` has collected them since the port landed: the kernel was right and the two userspace scripts were never given the same treatment. **Why it was invisible here:** clang 18 emits small-data sections and clang 23 does not, and this machine runs 23 while CI runs 18. The fix is a no-op locally -- the RISC-V application is byte-identical at 58,792 before and after -- which is exactly what a correct fix for a defect this machine cannot see should look like. **Evidence, in a container matching the runner (Ubuntu 24.04, clang 18.1.3):** before, `helloworldc99 exited status=1 syscalls=1`; after, `status=0 syscalls=87`, `c99-runtime-smoke exited status=0 syscalls=259`, every hosted application reporting zero orphan small-data sections, and `QEMU smoke boot reached all full userspace/resource markers`. |
| B-62 | The Fusion soak's session tally counts closes it never counted accepts for | VMware Fusion ARM64 | `TESTING` | A soak run reported `accepted=2515 closed=2516 outstanding=-1` after its 330 s settle, which reads as a connection the guest closed without accepting. **It is a counting artefact and not a leak.** Counted from the guest's own console: 2515 `net_accept`, 2516 `net_close`, and the extra close is `sockfd=6`, which `net_listen protocol=17 port=24002 sockfd=6` shows is the **UDP listening socket**. The tally counts every `net_close` while counting only TCP accepts, so any non-accepted descriptor makes it negative. `free_page_trend` is `delta_pages=0` across 1257 samples, so nothing is leaking. **To close:** count closes of accepted sockets only, so the figure means what its name says. **What the same run did not explain** is the failure it was reported for. Round 545's `sftp exited 255 ('Connection closed')` has no anomalous close in the guest log -- the connection at that point closed as an ordinary `client-disconnect`, so the drop was not visible to the guest at all. Two unrelated anomalies did occur, neither of which failed the soak and neither of which is round 545: `auth-timeout` at connection 1550 held 120,003 ms, and `packet-read-failed` at connection 2156 held 30,002 ms, preceded by a rejected `net-send-failed`. Both are round numbers -- 120 s and 30 s -- so both are timeouts firing, not transport loss. They are recorded here rather than given rows of their own until one of them recurs. |
| B-39 | `core-os-rc`'s fragmentation step timed out once here, and times out on every CI run | all four | `TESTING` | **Measured rather than waited for.** Five consecutive runs of `qemu-outbound-fragmentation-gate` on this machine: 98, 97, 97, 96, 98 seconds against a 360-second budget -- 26 to 27%, at load 2.07 to 2.88. So the budget is not marginal here and drift does not explain anything: the one local timeout means the step took **at least 3.7x** a runtime that is otherwise consistent to within a second. That remains unexplained, and the per-step elapsed/load instrumentation is what a recurrence will now speak through. **The CI half is a different problem and is fixed.** Budgets scaled by architecture and by nothing else, so nothing accounted for a host with no hardware virtualisation, where every guest is interpreted. `qemu_gate_lib.timeout_scale` reads `XAIOS_GATE_TIMEOUT_SCALE`, declared by the environment rather than sniffed at, and CI sets 3. A scale below 1 is clamped, because it would only tighten budgets. **A second thing the measurement found:** the aggregate's budgets total 188 minutes while its CI job's cap was 50, so any budget above the cap could never fire -- a hung step would surface as an anonymous job timeout rather than by name, which is precisely what this row exists to prevent. The cap is now 90. **To close:** a local recurrence, which now describes itself. |

| B-59 | A machine with no entropy source panicked at boot, in the self-test that exists to prove it refuses gracefully | all four | `entropy_is_production_grade()` requires both a good source label and a pool that was actually seeded. `entropy_swap_source_for_test()` moves the label and nothing else, so the `admin-control` self-test swapped in `DEVICE_RNG`, asserted the host-key gate would then return OK, and on a machine with no random device the pool is never seeded -- the gate correctly refused, and `admin_control.c:1278` killed the machine. | E3 | NUMA correctness | `TESTING` | The self-test proved node-0 placement and never checked node 1, so an allocator ignoring its node argument would have passed. | E4 | Multiqueue and RSS networking | `TESTING` | Per-queue driver state, every advertised pair allocated and polled round-robin so a busy pair cannot starve the others, and `VIRTIO_NET_CTRL_MQ_VQ_PAIRS_SET` sent only after the buffers exist. RSS is now negotiated and configured from the device's own config -- supported hash types, table length and key size read rather than assumed -- and steering is measured by `make qemu-rss-steering-gate` on a four-queue tap: sixteen buckets across four pairs spread `[64, 62, 66, 64]`, and a one-bucket control collapses to `[256, 0, 0, 0]` and fails the same assertion. Two defects were found by insisting on real counts: the hash key's byte 13 was zero, which pinned the low bit of every flow's hash so only even buckets were reachable (512 frames landed `[37, 0, 27, 0]` -- enough spread to pass a gate that asked for "more than one queue"), and `max_tx_vq` was sent as an index where the device reads a count, cutting a four-pair device to three with pair 3 set up, polled and unreachable. **Remaining:** the gate needs Linux, root and a multi-queue tap, so it runs on the Intel host only -- macOS offers the feature bits on both transports and has no multi-queue backend for either, and virtio-mmio multiqueue is unexercised anywhere. Hash report is offered but deliberately not negotiated: it grows every frame's header and forces software hashing for a per-packet value nothing here reads. |
| E5 | xaibootFS and xaiFS at scale | `TESTING` | xaibootFS v6 records a file as extents rather than a block list, which lifts both limits at once and makes a node smaller: 1 GiB per volume against v5's 4 MiB, 1024 nodes against 256, and a format limit of a gibibyte per file. The write path still refuses at 256 KiB, because it stages a whole file through a static buffer that was never raised with the format -- refusing is deliberate until it streams. Resident cost is about 850 KiB for 256 times the capacity. Which version a new volume gets follows the disk rather than a flag day. **Remaining:** scale evidence on physical storage. |
| E6 | Cluster data plane | `TESTING` | A sealed frame crosses a real network between two guests. `make qemu-cluster-two-node-gate` and `-three-node-gate` run join, partition, recovery and ownership, each phase on its own TCP connection so each machine has to be ready on its own schedule. `engine/src/cluster.c` had framing, sealing and peer state since it was written and had never opened a socket. **Remaining:** distributed execution, which waits on D-05. |
| E7 | Storage throughput, caching and power-loss evidence | `TESTING` | The block path moved 512 bytes per virtqueue round trip -- `buffer_size` had always been validated and then ignored. Raising it to a mebibyte and reading each byte once rather than twice changed the figures by orders of magnitude, against a baseline rebuilt from the same tree rather than remembered. Power loss is real: `make qemu-power-loss-gate` replays QEMU's `blklogwrites` journal through `tools/xaios_write_log.py`, because no emulator option loses an acknowledged write on its own. **Remaining:** physical storage; emulator figures are not throughput evidence. |
